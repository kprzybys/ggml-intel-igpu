# backend does not compile: ggml-openvino/utils.cpp:348 uses ov::ProfilingInfo::start_time (newer API).

# OpenVINO supports FP16 and quantized models, not F32 -> F16 model only.

## Prediction (written before the first run)
Facts: OpenVINO 2026.1 FP16 GEMM n = 4096 on this GPU: 305 GFLOPS with B as an input, 547 with B constant
(results/compare-openvino-2026-11-11.txt); gen9blas FP16 699. The backend compiles the whole ggml graph into one
OpenVINO model on the GPU (weights constant, attention and the other ops fused on the GPU, no CPU ops in between).
[HYP] pp512: weight GEMM 1299 GFLOP at ~550 GFLOPS = 2.4 s + other ops on the GPU 0.2-0.5 s -> 2.6-2.9 s ->
      175-195 t/s, i.e. close to GEN9 (176-178), maybe faster because nothing runs on the CPU.
[HYP] tg128: 3.1 GB of weights per token at ~20 GB/s + per-token graph overhead -> 4-6 t/s (ggml-cpu F16: to measure).
[HYP] Risks: the pip 2026.1 package may not build or run with this backend (2026.4.1 required); Gen9 untested upstream;
      first-run graph compilation takes seconds (excluded by llama-bench's warm-up only if the graph is reused).

## Against the prediction
- pp512 175-195 t/s: confirmed (184.4). OpenVINO is 4 % faster than GEN9 although its FP16 GEMM is slower
  (547 vs 699 GFLOPS): it runs the whole graph on the GPU, while GEN9 leaves every op except MUL_MAT on the CPU.
- tg128 4-6 t/s: wrong, 7.3 t/s. But ggml-cpu F16 already does 6.9 t/s: token generation is memory-bound on both
  sides of the shared memory bus; the GPU gains only 5 %.
- Perplexity: both GPU paths within 0.5 % of the CPU; OpenVINO differs more (-0.13 %, different numerics end to end).

## Consequences for the GEN9 design (docs/ggml-backend-design.md)
- Step 2 (token generation on the GPU) has little speed to win for F16: CPU 6.9, OpenVINO 7.3 t/s; the design's own
  model predicted 2.8-5.3 t/s for GEN9 with per-split submission, i.e. slower than the CPU. The case for step 2 is CPU
  time (OpenVINO: ~75-89 s CPU per run vs GEN9 ~255 s, mostly the CPU doing token generation), not t/s.
- For prompt processing the remaining gap to OpenVINO (4 %) is the CPU ops between MUL_MATs; with the faster GEMM,
  moving the elementwise ops / attention to the GPU would be the way past OpenVINO, not GEMV.
