# llama.cpp (2cbe0ec) GGML_BLAS=ON (OpenBLAS 0.3.26) on i5-8265U + UHD 620: OpenBLAS vs LD_PRELOAD libgen9blas_blas.so
# Model: Qwen2.5-1.5B-Instruct, F32 GGUF (converted from the official fp16 GGUF with llama-quantize ... F32)
# Why F32: ggml-blas.cpp (lines 70-103) converts non-F32 weights to FP32 on the CPU before every cblas_sgemm; F32 skips it.

## Prediction (written before any measurement)

Facts from the source (ggml/src/ggml-blas/ggml-blas.cpp, 2cbe0ec):
- MUL_MAT goes to BLAS only if ne0, ne1, ne10 >= 32 (line 420-431): prompt processing (pp) yes, token generation (tg) no.
- Call: cblas_sgemm(RowMajor, NoTrans, Trans, ...) once per (i02, i03) plane.

Model shapes (hidden 1536, FFN 8960, 28 layers, KV heads 2 x 128): per token per layer
2 * (2*1536*1536 + 2*256*1536 + 3*8960*1536) = 93.6 MFLOP -> 2.62 GFLOP/token -> pp512 ~ 1340 GFLOP in weight GEMMs.
Largest call: M = 512 tokens, N = 8960, K = 1536: 14.1 GFLOP, ~47 ms at 300 GFLOPS (far below the 640 ms preemption limit).
Weight matrix per FFN call: 8960 x 1536 FP32 = 55 MB in ordinary host memory (userptr path, not USM).

[HYP] OpenBLAS (8 threads) on these shapes: 200-300 GFLOPS -> 4.5-6.7 s of GEMM per pp512 -> pp512 ~ 70-110 t/s.
[HYP] gen9blas: 200-300 GFLOPS (host memory, userptr, per-call setup) -> pp512 within +-30 % of OpenBLAS,
      but process CPU during pp far lower (OpenBLAS ~770 %; gen9blas: only the non-GEMM ops on the CPU).
[HYP] tg (batch 1): no change (stays on the CPU, ggml-cpu).
[HYP] perplexity: equal to OpenBLAS within 0.1 % (FP32 accumulation on both sides).
Falsified if: gen9blas pp512 < 0.7x OpenBLAS, or perplexity differs > 0.1 %, or GEN9BLAS_BLAS_INFO shows the big calls on the CPU.

## Verdict against the prediction
- pp512 OpenBLAS 70-110 t/s: confirmed (81, first run 108).
- gen9blas pp512 within +-30 % of OpenBLAS: borderline. 0.78x the warm OpenBLAS mean (inside), 0.58x its first run
  (outside). Not faster in time.
- CPU "far lower": partly. 180 % vs 510 %, i.e. 2.8x less CPU, not the ~10x of a plain SGEMM call. [HYP] the rest is
  ggml-cpu's own ops plus its 4 worker threads waiting (spinning) while the BLAS call runs on the GPU: to check with perf.
- tg: not re-measured with gen9blas (batch 1 does not reach ggml-blas, min_batch = 32).
- Perplexity equal within 0.1 %: confirmed (0.001 %).
- Effective 164 GFLOPS vs ~340 for SGEMM alone: [HYP] per-call cost of 55 MB host weights (userptr pin/unpin of each
  weight matrix on every call, 196 calls per pp512) and serial non-GEMM ops between calls. Next step: per-call
  timing (GPU time vs wall) for one FFN call; keeping weights resident needs a ggml backend, not a BLAS shim.

## Comparison with other GPU paths: prediction (written before measuring)

A. CLBlast 1.6.2 (Ubuntu package, NEO 24.35) behind the same ggml-blas path, through a ~60-line cblas_sgemm shim
   (bench/compare/clblast_cblas.c): per call, copy A and B into new cl_mem buffers, CLBlastSgemm, read C back.
   Facts: CLBlast SGEMM square 248 GFLOPS at n = 1024, 44 at n = 4096 (results/compare-l3-power-2026-11-11.txt).
   [HYP] On these shapes (M = 512, K = 1536 or 8960) 80-200 GFLOPS of kernel time, plus copying ~55 MB per FFN call
   (~10-20 ms) -> pp512 25-55 t/s, i.e. gen9blas 1.1-2.5x faster on the same path. Perplexity equal within 0.1 %.
B. llama.cpp Vulkan backend (Mesa ANV 25.2.8), whole model on the GPU (-ngl 99), weights resident.
   Facts: ggml-vulkan MUL_MAT f32 square 111-142 GFLOPS (results/compare-ggml-vulkan-2026-11-11.txt), no copies.
   [HYP] pp512 ~ 1340 GFLOP / 110-140 GFLOPS + attention -> 40-60 t/s (below gen9blas-through-BLAS at 63);
   tg128 memory-bound like the CPU (~2-2.5 t/s); process CPU low (< 120 %). Perplexity equal within 0.1 %.

## Time breakdown of pp512: prediction (written before measuring; IOMMU off)
Tools: bench/compare/sgemm_timer.c (wall time inside cblas_sgemm per shape, LD_PRELOAD in front of the BLAS),
KCL_PHASES=1 (kcl submit phases), KCL_PROFILE_KERNELS=1 (GPU time per kernel name: packing vs GEMM vs epilogue).
Found while preparing: KCL_USERPTR_MB defaults to 1024 MB, the F32 weights are 6.2 GB, so the userptr cache cannot hold
them and every weight matrix is pinned again on every pass.
[HYP] gen9blas, ~7.7 s per pp512: 5.5-6.5 s inside cblas_sgemm, 1.2-2 s in ggml-cpu ops; inside sgemm: GEMM kernels
      ~4 s (340 GFLOPS), packing of the transposed weights 0.5-1 s, pinning ~0.15 s (IOMMU off), the rest waits/launches.
[HYP] OpenBLAS: ~6 s of 7.6 s inside cblas_sgemm.
[HYP] KCL_USERPTR_MB=8192 (weights stay pinned between passes): +2-6 % pp512.
